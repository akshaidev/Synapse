Project Synapse

Golden Hour ATM Cash-Out Interception — What Is Actually Implemented
Scope of this document: This describes the system as it exists in the current codebase — every claim below is traceable to a specific file, function, or endpoint. It does not describe planned features, PRD aspirations, or roadmap items unless explicitly marked as such. Where the original PRD specifies something that is not built, that gap is stated directly.
Internal Technical Reference  ·  MVP, Single-Process Deployment

1.Mission & Scope Boundary

Synapse predicts the physical ATM location where a cyber-fraud mule account will attempt to withdraw stolen funds, within a 120-minute "Golden Hour" window from the fraud's most recent transaction, and triggers an automated bank freeze webhook and/or a tactical dispatch recommendation.

What Synapse is not: it is not a general fraud fund-tracing system. Cases where the terminal account is a Crypto P2P off-ramp, a POS merchant, or a non-ATM-capable account are deliberately rejected (NO_VIABLE_ATM_MULE) and fall out of the pipeline entirely — this is a scope boundary matching the underlying problem statement, not an oversight.

Deployment precondition: the fund-flow DAG traversal (Section 4) assumes full visibility across every hop, including inter-bank transfers. A single bank running this system in isolation would lose visibility the moment funds leave to an external bank via IMPS/UPI/NEFT. The system is architected to sit at a central switch or investigating-cyber-cell level with cross-bank visibility — not inside one bank's own systems.

2.Architecture — What's Actually Running

Layer Implementation
API framework FastAPI, single process (api/main.py), no ASGI worker pool
Data validation Pydantic v2 models (api/schemas.py) — every payload, webhook, and internal request body is a typed model
Core algorithms core/graph.py, core/temporal.py, core/cluster.py — pure functions, zero FastAPI/HTTP imports
Persistence Flat JSON files under data/ — incidents.json, lien_registry.json, sent_crew.json — no database
Concurrency safety FileLock (the filelock package) wraps every disk write to the three JSON stores. A dedicated asyncio.Lock additionally guards the lien-initiate business logic (Section 6).
ATM registry Static JSON, 200 records, loaded into memory once at startup. Never modified at runtime.
Background jobs One asyncio task, started at app startup, sweeping _incidents every 60 seconds (Section 7)
Frontend Two static HTML files, vanilla JS, no build step — ui/index.html (main dashboard) and ui/feed.html (Bank Feed Simulator)
Authentication None. No login, no session, no RBAC, no TOTP. Any operator identity captured (Section 6) is a self-declared free-text field.

3.Ingestion & Golden Hour Gates

POST /api/v1/ingest accepts an IncidentPayload (NCRP ticket + fund-flow DAG + terminal mule intelligence) and runs it through two admission gates before any prediction happens:

Gate Logic Gate 1 — Fraud Recency: NOW() − max(txn_timestamp across all hops) ≤ 120 min. Fails → GOLDEN_HOUR_EXPIRED.
Gate 2 — Payload Freshness: NOW() − complaint_timestamp ≤ 240 min. Fails → STALE_PAYLOAD.

A X-Simulation-Mode: true header (or ?simulate=true) bypasses both gates and uses the payload's own ingestion_timestamp as the reference clock instead of wall-clock time — this exists purely so static demo payloads and automated tests produce deterministic, repeatable results.

4.The Three-Stage Pipeline

4.1Stage 1 — Terminal Mule Isolation (core/graph.py)

Builds a networkx DiGraph from the transaction list, identifies leaf nodes (out-degree 0), and scores each with a Mule Probability Score:

MPS Formula MPS = 0.30 × (amount / max_amount) + 0.30 × exp(−0.1 × Δt_minutes) + 0.40 × 𝟙[matches payload-declared mule]

The top-scoring leaf then passes a three-part viability filter: (1) must have a linked debit-card hash, (2) account type must be SAVINGS/BASIC_SAVINGS_BD/UNKNOWN, (3) bank/IFSC must not be in a hardcoded non-ATM-capable exclusion list (Paytm/Fino/Airtel/Jio/India Post payments banks). Failing any check produces an immediate HTTP 422 Unprocessable Entity rejection (NO_VIABLE_ATM_MULE: <reason>) and stops without persisting to _incidents or entering the dashboard — unifying Stage 1 viability failure with Gate 1 & Gate 2 ingestion rejections. This is the ATM-only scope boundary from Section 1, enforced in code.

4.2Stage 2 — Drain Time Engine (core/temporal.py)

Drain Time Formula B_accessible = min(balance, daily_limit − withdrawn_today)
drain_time = max(0, ceil(B_accessible / ₹20,000) × 4.5 min − τ), where τ = minutes elapsed since the latest transaction.
urgency = 0 if the daily limit is already exhausted; otherwise max(0, 1 − drain_time / 120).

The urgency-zero guard when the daily limit is exhausted is deliberate: a mule who legally cannot withdraw more today should never register as high-urgency.

4.3Stage 3 — Spatial ATM Ranker (core/cluster.py)

Estimates the mule's position via a priority cascade — combined cell-tower + IP, cell-tower only, IP-only (the primary MVP path, since live cell-tower/CDR data requires telecom authorization not available at MVP stage), or a static IFSC/city coordinate fallback. Then runs a brute-force Haversine scan against the 200-ATM registry:

Search & Scoring Search radius starts at 5 km (urban) or 15 km (rural), expanding ×1.5 up to twice if fewer than 3 ATMs are found.
RiskScore = 0.30×Proximity + 0.25×BankMatch + 0.20×CashStatus + 0.15×Offsite + 0.10×Traffic
Proximity is penalized by base_radius / active_radius — an ATM only found because the radius had to expand scores lower than one found in the initial pass.

If position estimation falls back to a static IFSC/city coordinate, a confidence_cap_applied flag is set, which caps the final composite confidence at 0.75 regardless of what the raw math produces (Section 5) — a low-confidence location estimate can never trigger a physical dispatch.

5.Confidence Aggregation & Intervention Tiers

Composite Confidence C = 0.20 × MPS + 0.35 × Urgency + 0.45 × RiskScore(top ATM), clamped to [0, 1], capped at 0.75 if the position estimate used a static fallback.
Confidence Tier Action
< 0.70 TIER_1_LOG_ONLY Logged, no webhook fired
≥ 0.70 PRIMARY_DIGITAL Freeze webhook fires automatically to /api/v1/freeze-card-atm (mock bank switch)
≥ 0.85 SECONDARY_PHYSICAL Same as above, plus flagged for tactical dispatch recommendation

Spatial confidence (weight 0.45) dominates the composite score — the system is, by construction, more sensitive to "do we know where" than "do we know who" or "how urgent."

6.Digital Lien Management

GET / POST /api/v1/liens manages a persistent freeze registry independent of the auto-pipeline.

6.1 Operator ID — Identity Without Authentication

Every destructive action in the system — initiating a lien, revoking a lien, dispatching a crew, resolving a case — requires an operator_id. This is a free-text string the operator types once into the Admin Drawer on the dashboard. It is stored in the browser's localStorage and automatically attached to every subsequent action in that session.

It is an asserted identity, not an authenticated one. There is no login, no session token, no mechanism to verify the string matches a real person. Its purpose is auditability, not access control: every lien record, revocation log entry, dispatch record, and resolution entry carries an operator_id, creating a traceable trail of who claimed to do what and when. If a case is later reviewed — in an audit, an NCRP inquiry, or an internal investigation — each action has a named responsible party attached to it, even if that name cannot be cryptographically verified.

The backend enforces its presence on lien actions via the LienActionRequest schema — an empty or missing operator_id returns HTTP 422. On the resolve endpoint, the same check applies: a resolution without an identified operator is rejected.

6.2 INITIATE and REVOKE

  • INITIATE requires a mandatory reason (collected via a modal, not a browser prompt()). On confirmation, it checks for a duplicate lien, fires a freeze webhook to the mock bank switch, records the lien with source: MANUAL, and persists to data/lien_registry.json.
  • REVOKE requires a reason. It moves the entry from active_liens to revocation_log — the history is never deleted, only reclassified.
  • A dedicated asyncio.Lock wraps the INITIATE path's check → webhook → write sequence, closing a race where two concurrent requests on the same account could both pass the duplicate check before either wrote — REVOKE does not need it, since it has no await between check and write and is already atomic under single-threaded async scheduling. This lock only holds under a single-process deployment — adding multiple uvicorn workers would give each its own lock instance and its own copy of the registry, reopening the race.
  • If the automated pipeline dispatches a Tier-1/Tier-2 freeze, it seeds the same registry with source: PIPELINE, so the UI shows "Revoke Digital Lien (Pipeline)" — manual and automatic actions share one source of truth.

7.Case Lifecycle, Resolution & the Sweeper

7.1 Human Resolution — POST /api/v1/incidents/{ncrp_id}/resolve

An operator resolves a case by submitting a resolution reason and optional note. The backend endpoint enforces: (1) the case must exist, and (2) it must not already be resolved (HTTP 409 idempotency guard). In both the dashboard (ui/index.html) and the Bank Feed Simulator (ui/feed.html), the resolution modal enforces that operator_id is configured (sharing state via localStorage key synapse_operator_id) and restricts resolution_reason to a fixed taxonomy:

Reason Code Meaning
FUNDS_FROZEN Bank confirmed card hold / lien took effect and funds are secured
MULE_APPREHENDED Field crew detained the mule at an ATM
FUNDS_RECOVERED Funds reversed to victim via bank reversal or court order
WINDOW_ELAPSED_CASE_CLOSED Operator manually acknowledges the window has passed and closes the case
FALSE_POSITIVE Incident was incorrectly flagged or based on faulty intelligence

On a valid resolve call, the handler sets resolved = True, stamps resolved_at, stores operator_id and resolution_note, then immediately fires the NCRP intimation webhook (Section 8). A corresponding POST /unresolve endpoint exists to reverse this — it clears resolved, resolved_at, resolution_reason, and resolution_note, returning the incident to the Active queue. The dashboard surfaces a "Reopen" button in the Resolved section for exactly this path.

7.2 Sweeper — Time-Based Disengagement

A background task sweeps every open incident every 60 seconds, enforcing two time-based states distinct from human resolution:

Condition Effect
6 hours since ingestion, status still PROCESSED or ACTIVE, and not human-resolved status → TACTICAL_TIMEOUT — real-time interception is considered moot; case is not marked resolved
30 days since ingestion, and never human-resolved status → ADMINISTRATIVELY_CLOSED, synapse_disengaged_at timestamp set — again, not marked resolved
Why "not resolved" matters here resolved = True is reserved exclusively for a human calling /resolve with an operator_id and a reason from the fixed taxonomy above. A sweeper-driven timeout is Synapse disengaging, not a confirmed outcome — conflating the two would mislead any future reader of the incident log (audits, NCRP intimation triggers, future training labels) into treating an unattended case as a solved one.

The dashboard reflects this as three mutually exclusive buckets: Active, Resolved (human), and Closed by System (TACTICAL_TIMEOUT / ADMINISTRATIVELY_CLOSED, each still carrying its own not resolved guard as a defensive check independent of the sweeper's own guard).

8.Outbound NCRP Intimation

A mock endpoint, /api/v1/mock/ncrp-intimation, exists and is called exactly once in the codebase: inside the human /resolve handler, immediately after an incident is marked resolved. It carries ncrp_ticket_id, operator_id, resolution_reason, resolution_note, and the resolution timestamp.

It does not fire on sweeper-driven closures — this is deliberate, not an oversight: a case Synapse gave up on after 6 hours or 30 days was never confirmed resolved, so telling NCRP "resolved" would be a false-closure signal. NCRP retains the complaint in its own queue throughout; Synapse never take custody of it, so a rejected or timed-out case is not something Synapse "hands back" — there is nothing to hand back.

9.Crew Dispatch

GET /api/v1/dispatch-registry and POST /api/v1/dispatch record which of the Top-3 ranked ATMs an operator has acknowledged and dispatched a crew to, backed by data/sent_crew.json under the same FileLock pattern as liens. State is shared across every browser session polling the dashboard — not per-operator localStorage, which was the original (and rejected) design.

10.User Interface

10.1 Main Dashboard — ui/index.html

Single-page dashboard served at / with two views. View A shows the incident queue, KPI counts, and all three status buckets (Active / Resolved / Closed-by-System). Clicking anywhere on an active incident row or its "Map →" action button immediately transitions to View B. Deep-linking via ?ncrp={ticket_id} URL parameter automatically selects and renders the target incident on initial page load. View B shows per-incident tactical detail: the Leaflet map with the mule's estimated position, tactical accuracy perimeters, and ATM markers; the intelligence panel (case overview, source account, terminal mule details, Location Intelligence & Telemetry Sources table, and transaction flow accordion with per-hop lien buttons and dedicated ATM_CASH_WITHDRAWAL cash-out badges); the interception countdown; and ATM dispatch cards. Both views poll /api/v1/incidents, /liens, and /dispatch-registry every 5 seconds.

10.2 Interception Countdown Timer

Displayed prominently in View B, the timer counts down live from drain_time_remaining_minutes (as computed at ingestion) toward zero. It has three distinct terminal states, each visually differentiated:

Terminal State Condition Meaning
INTERCEPTION WINDOW: CLOSED Timer hits zero during live countdown The mule's estimated withdrawal session has elapsed — field response is now operating past the predicted window
DAILY LIMIT EXHAUSTED drainable_today_inr ≤ 0 at ingestion time The mule had already hit their daily ATM cap before Synapse processed the case — no withdrawal urgency today; urgency score is explicitly forced to 0.0 (not computed)
NO WITHDRAWABLE BALANCE Account balance itself is zero or negligible Nothing to withdraw regardless of limits

The distinction between DAILY LIMIT EXHAUSTED and INTERCEPTION WINDOW: CLOSED is operationally important: the former means no urgency today (mule cannot act until midnight); the latter means urgency has passed — a different kind of bad outcome.

10.3 Bank Feed Simulator — ui/feed.html

A separate page served at /feed, used for testing and high-throughput demonstration. It has seven functional capabilities:

  • Single Upload with Simulation Mode: accepts an IncidentPayload JSON file. When Simulation Mode is toggled on, it dynamically aligns all payload timestamps to the current wall-clock time via alignPayloadTimestampsToNow(), ensuring the Golden Hour countdown begins fresh from upload while bypassing Gate 1 and Gate 2 admission checks. When Simulation Mode is off, payloads post to live ingestion (/api/v1/ingest) where Gates 1 & 2 are strictly enforced.
  • Bulk Payload Upload & 5-Second Paced Queue: accepts multi-file selection (<input type="file" multiple accept=".json">). Files are parsed into an in-memory queue preserving selection order. The queue engine dispatches the first payload immediately, followed by remaining staged payloads at strict 5.0-second intervals. A live visual telemetry panel displays Total Staged, Sent (with success/failure counts), Remaining, a fractional countdown timer (5s ... 0s), an animated progress bar, and the active ticket ID in flight. The engine is non-blocking: individual payload rejections (e.g. HTTP 422 NO_VIABLE_ATM_MULE) are logged to the Feed Activity Log without halting subsequent payloads. A "Cancel" button enables immediate mid-run termination.
  • Dynamic Timestamp Alignment & τ Invariance: to prevent static or historical payload timestamps from artificially exhausting the cash-out session time, alignPayloadTimestampsToNow(payload) shifts ingestion_timestamp, complaint_timestamp, all txn_timestamp entries, and cluster last_seen timestamps by the exact same offset Δ = Date.now() - T_base. Because (T_ingest + Δ) - (T_last_txn + Δ) ≡ T_ingest - T_last_txn = τ, the elapsed session time is mathematically invariant, preserving the designed non-zero interception window (e.g. 15.7m, 38.5m) and preventing premature auto-withdrawals or 6-hour sweeper timeouts.
  • Live Withdrawal Push with ATM Selection & GPS Pinpoint: allows an operator to select an active incident and choose from its Top 3 candidate ATMs via a dynamic dropdown (#atm-select), specify an amount, and click "Push Update to Synapse". Submitting hits PATCH /api/v1/incidents/{id}/live-update, which:
    • Updates the financial ledger: adds withdrawal to withdrawals_today_inr, subtracts from balance_inr, and recomputes drainable_today_inr.
    • Pinpoints suspect GPS location: directly updates suspect coordinates (mule_estimated_lat, mule_estimated_lon) to the exact latitude and longitude of the selected ATM, and sets mule_location_method to ATM_WITHDRAWAL_CONFIRMED.
    • Registers 3rd Location Source: records the event as the 3rd location source (Location Source 3: ATM Terminal Telemetry) in the Feed Activity Log, Stage 3 Spatial intelligence, and the dashboard's Location Intelligence & Telemetry Sources panel. On the Leaflet map, the suspect beacon switches to an amplified 22px emerald radar beacon (with a 46px outer glowing pulse wave, elevated to z-index 2500 above ATM markers) surrounded by an 800-meter tactical interdiction perimeter and an inner 300-meter cordon.
    • Logs Fund Flow Transaction: appends a discrete ATM_CASH_WITHDRAWAL hop to the incident's transaction ledger (payload_snapshot.transactions), rendering in the Transaction Flow accordion with dedicated cash-out badges.
    The main dashboard polls every 5 seconds and silently refreshes the map, location telemetry, and transaction flow without resetting active countdowns.
  • Cross-Dashboard Navigation: a top navbar link (🗺 Tactical Map & Dashboard ↗) and a direct action button (🎯 View on Tactical Map →) on the withdrawal confirmation card enable seamless one-click deep-linking into the Tactical Dashboard with the active incident pre-loaded in View B.
  • Case Resolution: a "Mark Resolved" action surfaced next to the active incident selector opening a dedicated resolution modal. It synchronizes with synapse_operator_id in localStorage, enforces a non-blank operator identity, provides the full 5-reason taxonomy dropdown, and dispatches POST /api/v1/incidents/{id}/resolve.
  • Feed Activity Log & Incident Purge: a running per-session log of every upload, withdrawal push, case resolution, rejection, and mode toggle. A dedicated "Clear Incident Feed" button calls POST /api/v1/incidents/clear to wipe in-memory and persisted incident records for clean demonstration rehearsals.

Both pages are unauthenticated static files served directly by FastAPI. There is no role separation — "View A / View B" describes two panels of one page, not the RBAC-gated Strategic Command vs. Tactical Operator portals the original PRD describes.

11.Testing & Assumptive Testing

11.1 Simulation Mode

Simulation Mode is toggled via a switch in the Admin Drawer on the dashboard, or by passing X-Simulation-Mode: true as a header (or ?simulate=true as a query parameter) directly to the ingest endpoint. When active, an amber ⚡ SIM MODE badge appears in the navbar.

Its effect is narrow and specific: both Golden Hour gates are bypassed, and the pipeline uses the payload's own ingestion_timestamp field as its reference clock instead of datetime.now(). This means a static demo payload with a fraud timestamp from weeks ago can pass Gate 1 and produce a meaningful drain time, because the system evaluates "how much time has elapsed" relative to a baked-in anchor, not the real clock. Nothing else changes — all pipeline math, confidence scores, and webhook dispatch logic run identically.

Simulation Mode exists purely for testing and demonstration. It is not a bypass that should ever be enabled in an operational deployment against real incident data.

11.2 Automated Withdrawal Simulation on Late Ingestion

When a payload is ingested and the computed drain time is already ≤ 0 at the moment of ingestion — meaning the mule's estimated withdrawal window has fully elapsed before Synapse received the case — the system does not simply display the original account balance. Instead, it automatically simulates the withdrawals the mule most likely already completed.

The simulation is not graduated — it does not scale withdrawal amount to how far past zero the timer has drifted. Whenever the drain timer has already reached zero at ingestion, the system floors the entire drainable_today_inr to the nearest ₹10,000 and simulates it as fully withdrawn in one shot. The dashboard then reflects this adjusted balance — not the pre-cash-out figure from the original payload — giving the operator a working estimate of what funds remain.

This is an assumptive inference, not observed data. The actual withdrawal amounts and timing are unknown; the system treats the worst-case (everything drainable was already taken) as the operative assumption. The first thing that should change when real case outcomes become available is validating this assumption against observed post-fraud ATM transaction logs.

12.Design Assumptions Built Into the System

These are constraints and decisions embedded in the running code — not configuration options, not roadmap items. Changing any of them requires code changes, not config edits.

Victim account is excluded from lien controls

In the Transaction Flow accordion, the first sender in the fund flow — the fraud victim — is hardcoded to never display a lien button. The exclusion is applied by the UI based on position in the hop list (the sender in Hop 1 is always the victim in a standard NCRP payload), not by any flag in the payload itself. Placing a digital freeze on the victim's account would compound the harm: they have already lost funds, and freezing their account would block access to whatever remains.

This is a correctness constraint, not a UX choice. An operator cannot accidentally initiate a lien on the victim through the dashboard — the button simply does not exist for that account slot.

4.5 minutes inter-withdrawal interval is a synthetic calibration constant

The baseline drain time formula uses 4.5 minutes as the average time between successive ATM withdrawals. This was calibrated against synthetic mule behaviour trajectories (AMLSim-derived), not real observed data. It directly controls how urgently Synapse classifies every case — a number that is too low produces over-urgent predictions; too high gives false comfort. This constant should be the first thing re-evaluated when real case outcome data becomes available.

IP geolocation is the primary location method at MVP

Cell-tower trilateration (the higher-accuracy location method) requires real-time CDR data from telecom operators. In India, tower dumps and CDRs are requisitioned under Section 91 CrPC / Section 94 BNSS through a formal legal process — they are not obtained unilaterally. (The older Telegraph Act interception framework has since been superseded by the Telecommunications Act, 2023.) This authorization step does not fit within Golden Hour latency, which is why the system falls back to IP geolocation. The location priority cascade is implemented correctly (cell tower → IP → IFSC fallback), but in practice every live incident at MVP will resolve to IP geolocation, which is typically city-block accurate (±1–5 km), not street-level.

13.What's Genuinely Modular, Ready for Production Swap-In

These are real seams in the current code — not aspirational, verified by reading the actual boundaries.

Core math has zero HTTP/framework dependency

core/graph.py, core/temporal.py, core/cluster.py take typed Pydantic inputs and return typed Pydantic results — no FastAPI imports, no request/response handling inside them. Any of the three can be lifted into a separate service, a batch job, or an ML-serving process without touching a line of routing code.

Outbound webhook targets are environment-driven, not hardcoded

MOCK_WEBHOOK_BASE_URL reads from SYNAPSE_BASE_URL (env var, default localhost:8000). Pointing the freeze webhook at a real bank switch, or the intimation webhook at a real CFCFRMS/NCRP endpoint, is a deployment config change — the calling code and payload shape do not need to change.

Every wire payload is schema-versioned

IncidentPayload.payload_version and FreezeCardATMRequest.webhook_version exist today. A future NCRP integration can introduce a new payload version alongside the current one without breaking the existing contract.

The ATM registry is a swappable data source, not baked into the algorithm

rank_atms() takes the registry as a plain list of dicts. Swapping the 200-record in-memory JSON for a PostGIS-backed query (as the roadmap already anticipates) means changing what populates that list at startup — the ranking math itself is untouched.

14.What Is Explicitly Not Built — Stated, Not Hidden

No authentication, RBAC, or audit-grade identity

Zero login, session, or TOTP anywhere in the codebase. Every operator_id is a self-typed string. If the PRD's RBAC/audit spec is a production requirement, it is unbuilt in its entirety — this needs to be a deliberate, scheduled scope decision, not something the documentation should imply is "mostly there."

Single-process only

The lien concurrency lock, the in-memory ATM registry, and the sweeper task all assume exactly one running process. Horizontal scaling (multiple workers/replicas) is not supported without redesigning state sharing.

No database

All persistence is flat JSON files with file locking. This works at MVP scale; it is not a production data layer — no indexing, no query language, no transactional guarantees beyond single-writer-at-a-time.

MPS and RiskScore weights are hand-tuned, not learned

Every β/γ/w coefficient in Sections 4–5 is a fixed constant chosen for the MVP, not fit against real fraud data. No false-positive rate has been measured against anything but synthetic payloads. This is a documented, accepted roadmap item (ML substitution via trained gradient-boosted models) — not a hidden gap, but worth restating plainly here.
